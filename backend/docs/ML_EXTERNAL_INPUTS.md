# Внешние признаки для ансамбля

Go-команда `cmd/ml-inputs` готовит почасовые погодные и occupancy-признаки для offline inference. Это отдельный этап подготовки входов: текущая HTTP-ручка и Publisher ещё не подключены к ансамблю 30 моделей. Созданный JSON не является готовым forecast bundle и не должен передаваться Publisher.

## Запуск из backend

```powershell
go run ./cmd/ml-inputs --occupancy "C:\Users\nikit\Downloads\occupancy_2025_popular_only.csv" --days 7 --output ml/generated/external-inputs.json
```

Каждый запуск получает новый прогноз. Выходной файл должен быть новым: команда отклоняет перезапись уже закреплённого snapshot. Для повторного запуска выберите другой output. CSV и сгенерированные JSON храните вне Git; каталог ml/generated игнорируется через ml/.gitignore.

## Occupancy

По указанию пользователя значения из 2025 года повторяются по московским месяцу, дню и часу для 2026 и других годов. Сохраняется исходный масштаб без деления на 100. Метка source=2025_synthetic сохраняется в snapshot, вместе с SHA256 CSV и reference_year.

Каждый час lag/rolling отдельно сопоставляется с календарным профилем. Например, occupancy_lag_1 для 2026-01-01 00:00 берётся из 2025-12-31 23:00. Rolling использует предыдущие 24/168 часов, без текущего часа. Это повторяемый исторический/синтетический профиль, доступный целиком до прогноза; он не выдаётся за фактическую occupancy 2026 года. Для 29 февраля при отсутствии такой даты в source year используется 28 февраля в тот же час. Пропуски и дубли вызывают ошибку, молчаливого заполнения нулём нет.

## Погода

Источник — https://api.open-meteo.com/v1/gfs, координаты по умолчанию 55.78, 37.58. Они задаются флагами latitude/longitude. Этот endpoint проверен живым запросом с шестью необходимыми признаками: temperature_2m, rain, snowfall, snow_depth, wind_speed_10m, wind_speed_100m. Единицы: °C, mm, cm, m, km/h, km/h. Другую высоту ветра не подставляем.

Используются конкретные почасовые значения, без усреднения по месяцу и без подстановки погоды 2025 года. Запрос timezone=Europe/Moscow; UTC offset и единицы ответа проверяются. Null, несовпадающие длины массивов и разрывы часов отклоняются.

Snapshot содержит время получения retrieved_at в UTC. Это время получения нами, не provider issue time. Для нового прогноза origin должен быть не раньше retrieved_at; исторический origin не может использовать текущий прогноз без утечки. weather_is_real=1 соответствует определению notebook: полные почасовые значения, включая API forecast; флаги partial/climatology равны 0. В UI источник следует называть прогнозом погоды, а не наблюдением.

API предлагает до 16 прогнозных дней (days 1..16). За пределами горизонта не придумываем прогноз и не подставляем климатологию. Клиент имеет timeout, ограничение размера ответа, обрабатывает HTTP ошибки. Команду запускают до закрепления forecast snapshot, а не отдельно при каждом пользовательском HTTP запросе.

Документация: https://open-meteo.com/en/docs/gfs-api

## Проверка

`go test ./internal/mlsources ./cmd/ml-inputs` — успешно. Проверены календарное повторение, граница года, UTC → Москва, leap-day fallback, rolling, дубли и NaN в occupancy, почасовая погода без усреднения, неверные единицы, null, разрывы и HTTP 429.

Живой запуск 2026-09-27 с пользовательским occupancy CSV сохранил 168 часов в ml/generated/external-inputs-20260927.json.
