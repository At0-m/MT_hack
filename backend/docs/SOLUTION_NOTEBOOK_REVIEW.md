# Проверка solution.ipynb и поставки моделей

Проверен исходный код notebook без запуска обучения. Результаты запуска и значения RMSE/WAPE в notebook отсутствуют. Размерность входов сопоставлена с ранее прочитанными ONNX из model_weights2.zip; численное соответствие Python и ONNX пока не проверено.

## Подтверждённая маршрутная часть

- Девять маршрутов: 1, 7, 11, 12, 17, 25, 26, 28, 50. На маршрут три модели с seed 42, 43, 239.
- Вход маршрутного ONNX: features, float32 [N,51]. Выход: predictions, float32 [N].
- Notebook берёт среднее конечных ответов сидов и ограничивает результат снизу нулём. При отсутствии конечных ответов выдаёт ошибку; при отказе одного сида меняет состав ансамбля.
- Лаги и rolling-признаки обновляются последовательно по часам. История до origin состоит из наблюдений, после origin — из прогнозов. Произвольная независимая обработка будущих часов не воспроизводит этот алгоритм.
- Часы 02:00 и 03:00 по Москве и маршрут 5 принудительно имеют нулевой прогноз. Округление для CSV: numpy.rint, половины к чётному.
- day_factor входит в признаки модели; дополнительное умножение готового прогноза на него notebook не выполняет.
- Порядок 51 признака сохранён в ml/reports/solution_route_contract.draft.json. Совпадение количества признаков не доказывает совпадение их порядка при обучении переданных весов.

## Ошибки в исходном коде

1. recursive_forecast сохраняет сглаженную историю `(1 - damping) * prediction + damping * seasonal`, затем сразу перезаписывает её `prediction`. Сглаживание не влияет на следующие лаги. Исправление изменит прогноз: нужно сохранить выбранное значение истории один раз, отдельно от выдаваемого prediction, и сравнить результаты на holdout.
2. Calendar._is_nonwork считает любую субботу/воскресенье нерабочими, хотя Calendar.features учитывает working_weekends. Длина праздничного блока и зависимые признаки могут противоречить is_day_off. Общая проверка нерабочего дня должна учитывать перенесённые рабочие выходные; зависимые признаки и day_factor должны использовать ту же проверку.
3. Occupancy в causal-режиме скрывает текущее будущее значение, но лаги и rolling читает из всей серии. После origin они могут брать будущие фактические значения. Ограничение доступности должно применяться ко всем occupancy-признакам, а не только occupancy_rate.
4. load_occupancy не задаёт часовой пояс для naive time и не проверяет конечность значений. Нужны явный timezone и согласованный диапазон occupancy_rate.

Режимы WEATHER_MODE=replay и OCCUPANCY_MODE=replay используют фактические внешние данные за прогнозируемый период. Это ретроспективный расчёт, а не доказательство качества прогноза с данными, доступными на origin.

## Погода

Notebook указывает старый open-meteo-msk.csv и WEATHER_TIMEZONE=Europe/Moscow. Пользователь ранее подтвердил UTC для старого файла: такой override сдвигает сопоставление часов на три часа. Для актуального open-meteo-55.78N37.58E151m (1).csv прочитана metadata Europe/Moscow, utc_offset_seconds=10800; этот экспорт уже московский. Нужно поменять путь на актуальный файл и читать его metadata без повторного сдвига UTC → Москва.

## Недостающие части поставки

Пользователь подтвердил смешивание: арифметическое среднее трёх глобальных LightGBM и среднее трёх CatBoost выбранного маршрута, затем `0.25 * LightGBM_avg + 0.75 * CatBoost_avg`. Веса сохранены в draft-контракте. Notebook задаёт clamp_zero для маршрутного ансамбля, но порядок ограничения нулём и округления для смешанного ансамбля требует эталонного примера; формула смешивания сама по себе этого не определяет.

- В notebook нет трёх глобальных LightGBM, порядка и подготовки их 17 признаков.
- occupancy_2025_popular_only.csv передан. Пользователь подтвердил повторение профиля 2025 по месяцу, дню и часу для 2026; реализовано в internal/mlsources. Погода берётся из Open-Meteo API. Подробности: docs/ML_EXTERNAL_INPUTS.md.
- Нужны эталонные входы/ответы именно переданных весов и итогового ансамбля, включая последовательный прогноз нескольких часов. Исправленная рекурсия должна иметь отдельный эталон.
- Нужен сохранённый ml_run_report.json с holdout-метриками и происхождением обучения поставленных моделей. Оценка уже обученных на train+test финальных весов на том же test не является независимой валидацией.

## Совместимость с Go backend

Текущий runtime принимает один ONNX с features → boardings и выходом [N,1]. Маршрутная поставка имеет другой output и форму; глобальная — ещё и другое имя и размерность входа. Простой замены файла недостаточно.

Prepared bundle требует конечные числовые признаки, а notebook допускает NaN в лагах, occupancy и погоде. Молча заменять их нулями нельзя: нужно согласовать представление пропусков и проверить соответствие CatBoost/ONNX.

Рекурсивный прогноз следует готовить последовательно в offline-контуре от закреплённого origin либо внедрять соответствующий алгоритм в отдельный адаптер. Усреднение и смешивание выполняются в памяти; промежуточные CSV не требуются. До получения глобального контракта и эталонов нельзя объявлять подключение всех 30 моделей завершённым.
