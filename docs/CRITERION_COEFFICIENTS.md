# Критерий: корректирующие коэффициенты и приём данных

## Что сделано

Интерфейс уже содержал поправки «Погода / События / Сезон» и реальный вызов POST /api/v1/scenarios/evaluate. Теперь валидные изменения автоматически отправляются через 450 мс после последнего ввода. Пустое поле и недопустимая точность не отправляются. Новое изменение отменяет предыдущий запрос через существующий dispatcher; ответ старого запроса не заменяет подтверждённый расчёт. Кнопка «Исходный прогноз» возвращает baseline.

Сохраняются явное окно сценария и ранее выбранный выпуск. Поправки отправляются backend, frontend не генерирует прогноз самостоятельно. Сервер применяет weather * event * season к базовому почасовому boardings только в effective_window, затем суммирует скорректированные часы. Он не применяет поправки повторно поверх предыдущего сценария.

Добавлен Go-импорт предоставленных train_route_flow_15min_clusters.csv и route_flow_15min_clusters.csv. Из восьми категорий билетов проверяется сумма total; в target включается только total, без двойного счёта. По route/date/hour складываются посадки, а не среднее четырёх интервалов. Порядок строк и файлов не влияет на labels.csv. Отчёт хранит версии алгоритма, SHA256 источников, SHA256 результата, часовую зону и частичное покрытие.

## Как показать интерфейс

1. Запустить существующий объединённый backend/frontend по INTEGRATION_README.md.
2. Войти, выбрать маршрут и период.
3. Открыть панель инструментов (иконка ключа), нажать «ПОПРАВКИ».
4. Изменить «Погода» с 1 на 1.2. После короткой паузы сервер вернёт scenario, изменятся числовые значения и визуализация.
5. Изменить «События» и «Сезон». Например, 1.2 * 1.1 * 0.9 = 1.188 от baseline в окне сценария. За пределами окна значения сохраняются.
6. Нажать «Исходный прогноз», показать восстановление значений. Экспорт CSV использует подтверждённый серверный calculation ID.

Это ручные сценарные множители, а не измерение причинного влияния погоды/событий. Критерий не подтверждает качество или подключение всех реальных ML-моделей.

## Воспроизводимый импорт

Из каталога backend, после выбора семантики dt_15min:

```powershell
go run ./cmd/ingest-flow --timestamp-position start --allow-partial --output flow-import-1 `
  "C:\Users\nikit\Downloads\train_route_flow_15min_clusters.csv" `
  "C:\Users\nikit\Downloads\route_flow_15min_clusters.csv"
```

Параметр timestamp-position обязателен. start означает начало 15-минутного интервала; end — его конец. Для end точка 00:00 относится к последнему часу предыдущего дня. Название dt_15min само по себе не подтверждает семантику: перед подготовкой конкурсных labels её нужно сопоставить с документацией источника/официальными labels. Проверочные результаты ниже относятся к явно заданному start.

Дубликаты route/quarter, включая перекрытие файлов, вызывают ошибку. Неизвестные маршруты, неверные timestamps, отрицательные/дробные/NaN значения и расхождение total с категориями отклоняются. Новая директория output обязательна: прошлый импорт не перезаписывается. В ней появляются labels.csv (route;date;hour;boardings) и report.json.

Без allow-partial импорт отклоняет неполные часы. С этим флагом сохраняются только наблюдавшиеся суммы, а report.json явно перечисляет observed_quarters. Неизвестные часы не заполняются нулями. Такие неполные суммы нельзя выдавать за полный час без согласованной политики покрытия. Output нормализует историю для ML; он не обучает модель и не публикует forecast snapshot автоматически. Следующий этап остаётся существующим ML/prepared bundle → Publisher с его проверками и транзакционной активацией.

Повторить команду с output flow-import-2, сравнить:

```powershell
Get-FileHash flow-import-1/labels.csv, flow-import-2/labels.csv -Algorithm SHA256
```

- Go-тесты internal/ingest, cmd/ingest-flow, internal/engine, internal/telemetry: успешно. Добавлен тест совместного действия трёх факторов до агрегации.

- Два импорта пользовательских CSV: 262485 строк, 65628 наблюдаемых часов, 59667753 посадки, 27 неполных часов. SHA256 labels.csv в обоих запусках: 794bce490e604e311af4636f2c01d4ab3f031a1a9b0c854a1c6e7dd864dc0661.
- Без allow-partial импорт ожидаемо отказал на 27 неполных часах.

Отчёт реального импорта: integration/verification/flow-import-report.json. Он содержит hashes, статистику и частичное покрытие; сами исходные CSV и полученные labels в архив не включены.

Браузерную проверку можно повторить из frontend:

```powershell
$env:PLAYWRIGHT_CHANNEL = "msedge"
pnpm exec playwright test --config playwright.factors.config.ts
```

Без PLAYWRIGHT_CHANNEL нужен установленный Chromium Playwright. Основная real-stack suite остаётся отдельной: playwright.config.ts. Полный Docker/PostgreSQL/native ONNX запуск и финальную конкурсную метрику эта проверка не подтверждает.
