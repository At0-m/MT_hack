ML-командой передан ансамбль из трёх глобальных LightGBM и 27 маршрутных CatBoost: девять маршрутов, по три seed 42/43/239. Подтверждённая формула — 25% среднего глобальных моделей и 75% среднего моделей выбранного маршрута. Notebook описывает 51 маршрутный признак и рекурсивное построение прогноза. Наличие весов не означает, что полный ансамбль уже подключён к веб-сервису: подготовка 17 глобальных признаков и численная проверка полного ансамбля пока не подтверждены. ## 2. Внешние данные

Погода: Open-Meteo GFS API — https://open-meteo.com/en/docs/gfs-api

Описание Go-адаптера погоды и occupancy: https://github.com/At0-m/MT_hack/blob/dev/backend/docs/ML_EXTERNAL_INPUTS.md

Внешние источники, указанные ML-командой:

- Историческая погода: https://open-meteo.com/en/docs/historical-weather-api
- Месячный пассажиропоток по видам транспорта Москвы: https://data.mos.ru/opendata/62521
- Moscow Parking Occupancy (4.6M snapshots): https://www.kaggle.com/datasets/danilmatrosov/moscow-parking-occupancy
- Календарь праздников РФ, библиотека holidays: https://pypi.org/project/holidays/

Источники перечислены по подтверждению пользователя. Производные CSV и правила их преобразования следует приложить к ML-поставке для воспроизводимости; ссылка на исходный dataset не заменяет конкретную версию используемого CSV.

Погодный адаптер получает почасовые температуру, дождь, снегопад, высоту снежного покрова и ветер на 10/100 м. Часовая зона — Europe/Moscow; единицы и полнота ответа проверяются. Occupancy берётся из производного occupancy_2025_popular_only.csv с меткой 2025_synthetic: для другого года повторяется тот же месяц, день и час 2025 года, без выдачи этих значений за фактические наблюдения нового года. Этот CSV не отождествляется с исходными 4,6 млн парковочных snapshots. ML-командой также переданы train_route_flow_15min_clusters.csv, route_flow_15min_clusters.csv и msk-data-trend.csv; преобразования и использование конкретными поставленными весами необходимо зафиксировать в ML DATA README. Календарные признаки РФ рассчитываются с holidays, школьные интервалы в notebook заданы вручную. Новостной источник не заявляется.

## 3. Веб-сервис, API и инструкция для жюри

Backend и запуск: https://github.com/At0-m/MT_hack/blob/dev/backend/README.md

Исходный frontend и запуск: https://github.com/At0-m/MT_hack/blob/dev/frontend/README.md

Контракт API: https://github.com/At0-m/MT_hack/blob/dev/backend/openapi/openapi.yaml

Backend написан на Go, данные хранятся в PostgreSQL/PostGIS. Основные API: POST /api/v1/forecasts/query, POST /api/v1/scenarios/evaluate, POST /api/v1/summaries/query и POST /api/v1/exports; доступны login/session/logout и health endpoints. Frontend — React/TypeScript с картой MapLibre. После отката восстановлен первоначальный frontend; он запускается отдельно по своему README. Единый запуск backend + frontend через Docker Compose в текущей поставке не подтверждён. Публичный адрес работающего сайта не предоставлен. Демонстрационный synthetic snapshot следует обозначать как demo, а не как результат реальной ML-модели.

## 4. Архитектура, область определения и адаптация

Схема архитектуры: https://github.com/At0-m/MT_hack/blob/dev/docs/ARCHITECTURE.md

Описание backend: https://github.com/At0-m/MT_hack/blob/dev/backend/docs/BACKEND.md

Контракт ML-данных: https://github.com/At0-m/MT_hack/blob/dev/backend/docs/ML_DATA.md

Целевая величина — количество посадок по маршруту, московской дате и часу. Приём route-flow данных выполняет валидацию и суммирование 15-минутных интервалов; далее ML-контур готовит прогноз и versioned inputs. Publisher проверяет подготовленный bundle и транзакционно активирует snapshot. API работает с закреплёнными версиями данных, модели и сети, выполняет агрегацию и сценарный пересчёт, отдаёт GeoJSON, summary и CSV. Перечень маршрутов, допустимые периоды и горизонт ограничиваются покрытием snapshot. Новые данные публикуются как новая версия, а не незаметно заменяют старые результаты. Остановочный прогноз требует отдельных данных/предсказаний и не выводится из маршрутного значения. Отдельный адаптер полного 30-модельного ансамбля остаётся задачей интеграции.

## 5. Производительность и дополнительные возможности

Benchmark-отчёт: https://github.com/At0-m/MT_hack/tree/dev/docs/benchmark

В пяти коротких HTTP-тестах выполнено по 5000 запросов при параллельности 4, 8, 16, 24 и 32 — всего 25000 запросов, ошибок 0. Максимум: 662,64 запроса/с при concurrency=24, p95=46,555 мс, p99=55,162 мс. При concurrency=16: 660,52 запроса/с, p50=23,517 мс, p95=33,522 мс, p99=40,510 мс. При concurrency=32: p95=61,659 мс. Каждый основной запуск длился примерно 7,5–8,8 с. Сырой JSON приложен для c=16 и smoke; остальные строки подтверждены переданным summary.csv.

Измерения относятся к API напрямую (http://api:8080), одному route/day-запросу и synthetic snapshot demo-september-2026-v1. Характеристики сервера/БД, CPU/RAM, commit/image digest и эквивалентность текущей сборке не зафиксированы. Поэтому результаты не являются длительным soak-тестом, тестом всей цепочки frontend/gateway или оценкой качества ML.

Реализованы серверные сценарии выпуска и поправок спроса, календарные периоды, CSV-экспорт, сессии с HttpOnly cookie, проверка Origin, ограничение запросов, ограниченный кэш прогнозов и версионирование snapshot. Добавлен воспроизводимый импорт CSV с SHA256, проверкой дублей и отчётом покрытия. На переданных route-flow CSV: 262485 интервалов, 65628 наблюдаемых часов, 59667753 посадки, 27 неполных часов; два запуска дали идентичный SHA256 результата. Автоматические коэффициенты в интерфейсе были удалены при возврате исходного frontend и как действующая UI-возможность не заявляются. Конфигурации Prometheus/Grafana присутствуют в репозитории, но PNG из benchmark-архива являются графиками CSV, а не скриншотами Grafana.

## 6. Ограничения и план развития

Текущая поставка не подтверждает независимое качество полного ML-ансамбля и его полное подключение к веб-сервису. Synthetic demo и нагрузочные тесты не заменяют валидацию на отложенных реальных данных. Occupancy нового года — повторяемый профиль 2025 с синтетической меткой; доступность прогноза Open-Meteo ограничена горизонтом провайдера. В исходном ML notebook обнаружены ошибки обновления сглаженной истории, учёта рабочих выходных и доступности будущих occupancy-лагов; их исправление требует повторной валидации. Для 27 неполных часов нужна согласованная политика покрытия и подтверждение семантики dt_15min.

План развития: согласовать 17 глобальных признаков и эталонные ответы, подключить ансамбль 25/75 и проверить Python/ONNX parity; опубликовать независимые RMSE/WAPE и описание train/validation split; завершить проверку исходного frontend с реальным API и единый контейнерный запуск; вернуть UI-коэффициенты после согласования с frontend-командой; подключить реальные остановочные данные; автоматизировать обновление входов и snapshot; выполнить более длительные тесты, записать server/DB CPU/RAM, cache hit ratio и условия запуска; проверить масштабирование, мониторинг и восстановление после сбоев.
